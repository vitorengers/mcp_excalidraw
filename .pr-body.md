Closes #505.

The half that makes a paired device a feature rather than a one-time unlock: a surface that
lists the devices in the registry, lets the name be edited, and revokes one — on its next
request, and on its socket.

## What is here

**`GET /api/devices`, `PATCH /api/devices/:id`, `DELETE /api/devices/:id`**, on
`core/device-registry.ts` (#502, merged as #507 while this was being written — see *Reconciling*
below). The list never carries a stored hash; `self` names the caller's own entry when the
caller is one of them.

**Who may ask** is the only place in the API where *which* credential a caller holds changes the
answer:

- the **list** is the host's and a paired device's. A device that cannot see the list cannot see
  that it is on one, and would have nowhere to press *sign this machine out*;
- a **rename** is the host's. The name is the operator's word for a machine, and a device
  editing its neighbours' rows has no standing to;
- a **revoke** is the host's, and a device's own. **Revoking the device you are reading this on
  is allowed and warned about**, not refused: the operator on loopback cannot lock themselves
  out — the board token is a file and the host is not on the list — and a paired device signing
  itself out is legitimate.

**The socket half.** `DELETE /api/devices/:id` closes the sockets that device holds, with code
`4003` and a reason, and answers with how many it closed. This is the half a person cannot see
and the half that would otherwise still be sending: the upgrade streams the scene and every live
shell's scrollback for as long as it stays open, so an HTTP-only revocation takes a laptop off
the list, shows it gone, and goes on publishing the board and every terminal to it. Only that
device's sockets — the operator's own and a second device's are asserted to survive, because a
revocation that closed everything would pass the first case for the wrong reason.

**The surface**, `frontend/src/components/DevicesDialog.tsx`, opened by **Devices** on the
board's own bar. Beside the project settings rather than on the canvas, and on the bar rather
than behind the gear: the gear is drawn only on the tab in front, and this has to open on a
board with no project registered at all — which is the state a fresh clone is in. Each row
carries the name (editable), last seen and approved (relative, exact instant in `title`), the
address and the `Host`, and Revoke behind a confirmation that names the device.

**`docs/devices.md`** is the page a person is sent to when they ask *who can reach my board*,
linked from `docs/index.md` and carded on the board.

## Calls the issue left open

- **A device's credential is accepted at the token gate and at the WebSocket upgrade.** Without
  it, "the list is refused to a caller that is not the host or a paired device" and "a revoked
  device's next request is refused, its socket is closed" cannot be expressed at all, let alone
  checked. It is the minimum #505 needs and a subset of what #501 will do: that issue moves
  `offLoopback` from *where the server bound* to *who is calling*, and this change does not
  touch it.
- **These three routes are behind `offLoopback` like every other route that answers with
  something this machine owns.** Said plainly rather than hidden: on a board bound to an
  interface they answer 403 as the rest of the API does, so today this surface is the operator's
  on their own machine. Which credential a caller holds and which address the server bound are
  separate questions and both are still asked. #501 is where the second one changes.
- **`lastSeenAt` is written at most once a minute per device**, in `src/server.ts` and not in the
  registry — `touchDevice` deliberately leaves the rate to its caller. A write per request would
  rewrite the whole registry, with a `chmod`, for every poll of every panel, and "within the last
  minute" is as fine as the question this column answers ever gets.
- **Nothing here pairs a device.** #503 is the exchange and #504 the approval dialog; neither has
  landed, so on a real board this list is empty until they do. The checks seed the registry file,
  which is the whole of what the server reads either way.

## Reconciling with #507

`#502` merged as **#507** mid-run, bringing `src/core/device-registry.ts`. This branch had grown
its own `src/core/paired-devices.ts` because the dependency was still open; **that module is
deleted and everything here now sits on the one that landed.** The merged one is the better
design and it won on every difference: `<id>.<secret>` as one opaque credential (so a WebSocket
handshake, which has room for one query parameter, can carry it), a decoy compare so an unknown
id costs what a wrong secret costs, `lastSeenAt: null` as a real state — *paired and never used*
is a different answer from *last used in March* — and complain-once on a malformed file. The
surface renders `null` as `never` rather than flattening it to "unknown".

The overlap in the checks was cut rather than duplicated: `check-device-registry.mjs` owns the
file, its permissions and the compare, and `check-device-management.mjs` was trimmed to the
routes and to the one thing that is this surface's own — that a registry nobody can parse is an
empty list here and not a 500 on the board whose operator has just broken the file.
